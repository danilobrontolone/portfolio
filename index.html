Engineering Thinking

How I approach system design, tradeoffs, and hard problems—not just what I built.

Architecture & system design

I sketch flows before coding: orchestrator → agents → contracts. For healthcare intake, that meant Patient Input → Orchestrator → [Intake → Triage → Routing] → structured result. Clear boundaries between agents (Pydantic models, explicit handoffs) keep systems testable and debuggable at scale.

I use simple ASCII or Mermaid-style diagrams in docs and ADRs so the “why” is visible to the whole team.

Tradeoffs & technology choices

Why LangGraph for multi-agent: stateful graphs and checkpointing beat ad‑hoc chains when workflows get complex. Why Rust on the RAG path: latency-sensitive ingest and search needed a single binary and predictable performance. Why rule-based fallback in healthcare: systems can’t just fail when the LLM is down—conservative triage + human-review flags keep safety first.

I document “why not X” as much as “why Y” so future changes don’t repeat past mistakes.

Challenges & how I solved them

LLM output parsing: model sometimes returned markdown-wrapped JSON or extra text. Fixed with strict prompts, examples, Pydantic validation, and a fallback parser. Urgency classification drift: same symptoms, different phrasings → inconsistent levels. Added red-flag keyword detection and explicit criteria in the prompt. RAG precision: improved retrieval from ~60% to 75%+ with better chunking, embeddings, and optional reranking—measured so we could iterate.

I treat production issues as a feedback loop: add logging, metrics, and tests so the next failure is easier to diagnose.

Scalability awareness

I design for growth from the start: stateless agents so we can scale horizontally; vector search (e.g. Qdrant) and K8s for 100k+ docs; cost and latency budgets (e.g. token estimation, sub-second p95). I add observability early—structured logs, metrics, and alarms (error rate, latency, confidence)—so we see regressions before users do.
